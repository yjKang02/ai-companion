## 목표와 범위

캐릭터 원본으로 독립된 방을 만들고, 방 안에서 모델·메신저·페르소나를 편집하며 대화를 이어가는 개인용 시스템을 만든다. 실행 방식은 [로컬 서버 + 로컬 웹 UI](결정/002-로컬서버-웹UI.md)로 결정했다. 화면 요구는 [UI 설계](UI설계.md), 방의 독립성·삭제·재시작 보존 계약은 [기초 설계](기초설계.md)를 따른다.

첫 사용 가능한 버전의 목표는 ‘원본 등록 → 방 생성 → 웹에서 실제 모델과 대화 → 설정 편집 → 서버 재시작 후 재개 → 방 삭제’다. 메신저 연결과 일상 대화 스케줄러는 이 흐름 위에 순서대로 추가한다. 이는 구현 순서의 제안이며 기존 사용자 요구를 제외한다는 뜻이 아니다.

## 현재 코드와 설계의 차이

| 현재 코드에서 확인한 내용 | 다음 구현에 필요한 변화 |
| --- | --- |
| `ConversationKey`는 외부 주소·사용자로 구성 | 외부 서비스와 독립된 방 ID를 중심으로 저장·호출 |
| `InMemoryConversationStore`에 성공한 턴만 보관 | 입력·생성·전송 상태를 영구 저장하고 재시작 복구 |
| `ConversationService`가 공용 프롬프트·모델과 송신기를 사용 | 방별 컨텍스트·모델 설정과 입력·응답 경로 적용 |
| Discord·LM Studio 어댑터와 가짜 의존성 테스트 존재 | 기존 어댑터 경계를 활용하고 새 방 계약에 맞춰 회귀 검증 |
| 웹 서버·웹 UI·DB 마이그레이션·스케줄러 없음 | 아래 순서로 추가. 문서의 ERD를 구현 완료로 보지 않음 |

위 표는 기존 CLI 경로의 한계다. 새 [방 서비스](../src/ai_companion/application/rooms.py), [비동기 포트](../src/ai_companion/application/room_ports.py), [메모리 검증 어댑터](../src/ai_companion/adapters/room_memory.py), [조립 함수](../src/ai_companion/bootstrap.py)를 추가했다. 기존 CLI는 아직 새 경로로 전환하지 않았다. 책임과 변경 이유는 [백엔드 구현 설계](백엔드구현설계.md), 검증 결과는 아래 작업 목록에 기록한다.

## 구현 순서

아래는 의존성을 기준으로 정리한 권장 순서다. 상태·목표일과 완료 조건은 [작업 목록](#작업-목록)에서만 관리한다.

연결·실행 기반 B01을 출발점으로 웹에서 사용할 수 있는 최소 MVP를 먼저 만든다. B02 메신저 전환은 저장 구현의 선행 조건에서 빼고 I06과 함께 진행한다. 연결 계약과 변경 이유는 [백엔드 구현 설계](백엔드구현설계.md)에 계속 갱신한다.

- **연결·방 실행 구조 — B01.** 연결 정의·방별 모델 선택·실행 자원, 독립 방 ID·revision, 비동기 포트와 명시적 입력 경로를 만든다. 가짜 연결과 메모리 저장소로 두 방 실행·설정 변경·늦은 결과를 검증한다.
- **후속 메신저 전환 — B02/I06.** 메신저 연결의 공유·시작·중지와 명시적 방 바인딩, 생성·송신 분리 계약을 연결한다. 웹 MVP의 방·저장 기반 위에서 기존 CLI 수신 경로를 전환한다.

이후 순서는 다음과 같다.

1. **최소 구현 계약 확정 — I01.** [저장 결정](결정/003-내부연결DB-외부방별SQLite.md)에 따라 내부 연결·외부 프로파일·방별 DB를 분리한다. [현재 데이터 설계](데이터설계.md)의 DB 간 참조·중복 방지·삭제 복구와 [코드 전환 계약](백엔드구현설계.md)을 구체화한다. 프로파일 파일 형식·비밀 저장·마이그레이션 실행 정책은 확정 전 미정으로 남긴다.
2. **방 생성과 영구 저장 — I02.** I02A에서 내부 연결·바인딩·접수표를 먼저 SQLite로 저장하고, 이어서 방별 DB·registry·삭제 복구와 외부 프로파일을 연결한다. 프로파일 원본과 방 사본을 분리하고 생성·조회·편집·삭제를 구현한다. 실제 메신저와 모델 없이 두 방의 독립성과 재시작 복구를 확인한다. DB 전체 확장 테이블을 한꺼번에 만들지 않는다.
3. **로컬 웹 API — I03.** 연결·프리셋·프로파일·방의 등록과 편집을 API로 노출한다. 이 단계 시작 전에 웹 프레임워크와 로컬 접근 보호를 결정한다. 영구 저장을 완료한 뒤 성공을 반환하고 버전 충돌을 처리한다.
4. **최소 웹 화면 — I04.** 프런트엔드 기술을 정하고 좌측 탭·대화 프로필 홈·방 화면·우측 설정을 실제 API에 연결한다. 최초에는 방 생성·편집·삭제와 저장 결과를 확인한다. 스케줄러 미구현을 ‘실행 중’처럼 표시하지 않는다.
5. **영구 기록을 사용하는 실시간 채팅 — I05.** 가짜 모델로 입력·처리·응답·실패·재접속을 검증한 뒤 기존 LM Studio 어댑터를 연결한다. 입력 중복 키, 방별 처리 순서, 설정 변경·삭제 도중 늦은 결과 차단을 포함한다. 토큰 스트리밍은 별도 선택이다.
6. **웹 MVP 통합 검증 — I08A.** 원본 등록부터 방 생성·웹 대화·편집·재시작 재개·삭제까지 검증하고 로컬 서버 실행 안내를 제공한다. 메신저·스케줄러 완료를 기다리지 않는다. 실제 LM Studio 왕복과 지원 OS는 검증한 범위만 표시한다.
7. **외부 메신저를 같은 방에 연결 — B02/I06.** 기존 Discord를 새 방 ID와 기록에 연결해 경계를 먼저 검증한다. Telegram 채택 여부는 토픽·계정 연결 검증으로 결정한다. 웹과 메신저의 동시 입력, 응답 목적지와 복제 전송 정책을 이 단계 전에 확정한다.
8. **일상 대화 스케줄러 — I07.** 방별 ON/OFF·다음 실행·오류 상태를 연결한다. 수동으로 지정한 단순 일정부터 시작하는 안을 제안하며, 자동 일정 추출은 필수가 아니다. 중복 실행 방지·종료·절전 복귀·놓친 일정·전송 결과 불명을 검증한다.
9. **확장 통합 검증 — I08B.** 메신저·스케줄러와 웹의 동시 사용, 재시작·삭제·송신 결과 불명을 추가 검증한다. 기존 I08을 I08A/B로 나누어 웹 MVP 완료 조건과 구분한다.

I01A·I01B에서는 I01의 저장 경계에 맞춰 방 콘텐츠와 내부 실행 바인딩, 외부 입력 식별자를 분리한다. I02에서는 기존 메모리 계약 테스트를 실제 파일·DB 재열기 테스트로 확장한다. I03~I05와 I08A를 거치면 웹에서 사용할 수 있는 첫 결과가 나온다. 실제 키 등록 전에 비밀정보 저장 방식을 정한다.

최소 MVP의 수용 기준은 다음과 같다. 이 목록은 검증 시나리오이며 별도 작업 상태표가 아니다.

- 같은 캐릭터 원본으로 두 방을 생성하고 컨텍스트·대화를 독립적으로 유지한다.
- 한 방에서 페르소나·모델 옵션을 편집해도 원본과 다른 방은 바뀌지 않는다.
- 웹에서 실제 모델과 대화하고, 화면 재접속·서버 재시작 후 같은 방과 기록을 읽는다.
- 잘못된 설정·저장 실패·동시 편집·모델 오류를 성공으로 표시하지 않는다.
- 방 삭제와 삭제 도중 재시작 후 해당 방 데이터만 제거한다. 지연 응답으로 방이 되살아나지 않는다.
- 모델 연결이나 외부 라이브러리가 없을 때 방을 초기화하지 않고 연결/접근 오류를 표시한다.

구현 전후 pytest·Ruff·mypy를 확인하고 실제 모델·메신저 접속은 오프라인 검사와 구분한다. CI 적용 범위는 [저장소 운영](저장소운영.md#자동-검사)을 따른다.

자동 기억 추출·관계/기분 계산·이미지 에셋·공유 패키지·트레이 앱은 이후 범위를 정한다. 외부 콘텐츠의 저장 경계는 I01에서 정하되 고급 공유·직접 파일 편집까지 첫 구현에 포함하지 않는다.

### 이전 목표와 MVP 범위 기록

아래 목표·수용 기준은 2026-09-17 변경 전 계획이다. 기존 검토 근거를 보존하기 위한 것으로 현재 MVP의 확정 범위가 아니다.

짧은 일상 대화를 이어 가는 개인용 AI Companion을 만든다. 메신저와 모델이 바뀌어도 대화·페르소나·개인 데이터 관리 로직을 재사용할 수 있는 객체지향 구조를 목표로 한다. 사용자가 현재 적용되는 페르소나와 저장된 개인 데이터를 직접 확인하고 수정·삭제할 수 있어야 한다.

원문에서 짧은 응답, 대화 연속성, local-first 방향을 가져온다. 원문의 컴포넌트 구성과 기술 스택은 참고 자료로 취급한다. 이번 요청에 따라 수동 데이터 관리 화면을 MVP로 앞당기고, 자동 기억 추출·관계 시뮬레이션·선제 메시지는 후속 검증으로 둔다.

### 최소 MVP의 제품 범위

| 영역 | MVP에 포함 | 이후 검토 |
| --- | --- | --- |
| 대화 채널 | 허용된 사용자 1명의 Discord DM, 텍스트 대화 | 다른 메신저, 서버 채널, 여러 사용자 |
| 모델 | 로컬 LLM과 외부 API를 같은 포트로 연결, 설정으로 선택 | 추가 공급자, 자동 라우팅·장애 시 자동 전환 |
| 대화 경험 | 짧은 응답 1개, 최근 대화 보존, 처리 중 표시 | 여러 메시지 분할, 인위적 지연, 선택적 무응답 |
| 페르소나 | 말투·성격·호칭·응답 길이 설정 조회와 수정 | 여러 캐릭터, 관계·기분·가상 일상 |
| 개인 데이터 | 사용자가 직접 등록한 사실 CRUD, 대화 조회·삭제 | 자동 사실·사건·일정 추출, 의미 검색 |
| 관리 화면 | 로컬 웹 화면, 저장 후 다음 요청 반영, 변경 상태 갱신 | 원격 접속, 모바일 최적화, 실시간 푸시 |
| 지속성 | 재시작 후 대화·설정·사실 복구 | 다중 서버, 분산 큐 |

초기 가정은 단일 사용자·단일 Companion·단일 프로세스다. 사용자 요청에 따라 Python·discord.py와 LM Studio로 첫 연결을 구현한다. 현재 개발 환경은 Windows·Python 3.13이며, 실제 운영 서버 OS·GPU·VRAM·RAM·모델 ID는 미정이다. 토큰과 런타임 데이터는 문서에 넣지 않는다.

### MVP 완료 시 확인할 결과

1. 허용한 계정이 Discord DM을 보내면 선택한 모델의 짧은 답변을 받는다. 로컬 LLM과 외부 API 각각에서 같은 대화 흐름을 검증한다.
2. 서버 재시작 후 최근 대화를 이어 가고, 저장한 페르소나와 사용자 사실이 유지된다.
3. 관리 화면에서 페르소나를 바꾸면 저장된 버전과 적용 시점을 확인하고 다음 요청에 새 값이 들어간다.
4. 사용자 사실의 추가·수정·비활성화·삭제가 가능하고, 대화 내용도 조회·삭제할 수 있다.
5. 삭제된 기록은 이후 모델 입력에 포함되지 않는다. 과거 대화에 같은 사실이 남아 있을 수 있으므로 관련 대화 삭제도 선택할 수 있다.
6. 모델 시간 초과, 중복 수신, 데이터 수정 중 생성, 비허용 사용자 접근 시 정해진 동작을 검증한다.

위 항목은 구현 수용 기준이며 실제 검증 결과가 아니다. 자연스러움은 별도 사용자 평가로 판단한다.

작업 상태·목표일은 아래 작업 목록 한 곳에서 관리한다. 이 표는 단계 간 의존성과 범위를 설명한다.
