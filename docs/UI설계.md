# 대화 프로필 중심 UI 설계

사용자가 제시한 화면 구상과 후속 검토 사항을 정리한 설계 초안이다. 화면 구성 요구의 원본은 이 문서다. 실행 형태는 [로컬 서버 + 로컬 웹 UI](결정/002-로컬서버-웹UI.md)로 결정했으며 프레임워크 선택과 구현은 남아 있다. 방의 데이터 소유·저장 계약은 [기초 설계](기초설계.md), 저장 구조는 [데이터 ERD](데이터설계.md), 작업 상태는 [프로젝트 문서](프로젝트.md#작업-목록)를 따른다.

화면 구현은 [구현 순서](프로젝트.md#구현-순서)에 맞춰 실제 저장 API 기반의 홈·설정, 실시간 채팅, 외부 메신저, 스케줄러 순으로 연결한다. 아직 제공하지 않는 동작은 미지원 상태로 표시하고 실제 실행 상태와 혼동시키지 않는다.

## 사용자가 제시한 화면 구성

- 좌측에는 각각의 설정으로 이동하는 탭을 둔다.
- 메인 홈 화면에서 생성한 대화 프로필들을 확인한다.
- 각 대화 프로필에서 캐릭터의 기동·정지 여부와 일상 대화 스케줄러 상태를 확인한다.
- 대화 프로필을 클릭하면 해당 방의 채팅 화면으로 이동한다.
- 채팅 화면에서는 메신저 앱처럼 실시간으로 직접 대화할 수 있다.
- 채팅 화면의 우측 설정을 열면 스케줄러 ON/OFF와 해당 채팅방 설정을 조작하는 패널이 나타난다.
- 구현 방식은 [로컬 서버 + 로컬 웹 UI](결정/002-로컬서버-웹UI.md)로 결정했다. 구체적인 프레임워크와 라이브러리는 아직 정하지 않았다.

## 용어와 화면 이동

이 문서에서 ‘대화 프로필’은 생성된 대화방과 그 방 전용 설정을 묶어 홈에 표시하는 항목으로 해석한다. 새 방의 재료인 ‘캐릭터 프로파일 원본’과 구분한다. 별도의 데이터 객체를 추가한다는 의미는 아니며 최종 화면 명칭은 후속 검토한다.

같은 캐릭터로 만든 여러 대화 프로필도 각자의 방 ID·대화·기억·설정을 유지한다. 홈에서 기존 항목을 선택하면 그 방을 재개하고, 새 대화 프로필을 만들면 독립된 방을 생성한다.

화면 이동은 ‘홈의 대화 프로필 목록 → 선택한 방의 실시간 채팅 → 우측 방 설정 열기’로 구성한다. 좌측의 공용 설정 탭은 캐릭터 원본·개인 페르소나·프롬프트·모델 연결과 프리셋·메신저 연결·앱 설정에 접근하는 용도로 제안한다. 정확한 탭 이름·순서·묶음은 미정이다.

## 홈: 대화 프로필과 동작 상태

생성한 대화 프로필을 목록 또는 카드로 표시한다. 표시 방식은 미정이며, 다음 항목을 제안한다.

| 표시 항목 | 목적 |
| --- | --- |
| 방 이름과 캐릭터 이름 | 동일 캐릭터의 여러 대화를 구별 |
| 일상 대화 스케줄러 ON/OFF | 사용자가 설정한 자동 대화 활성 여부 확인 |
| 실제 실행 상태 | 실행 가능·대기·중지·오류 등의 실제 상태 확인 |
| 다음 실행 시각 또는 예약 없음 | 일상 대화가 언제 예정되어 있는지 확인 |
| 모델·메신저 연결 상태 | 실행이 막힌 이유 확인 |

‘켜짐’이라는 설정과 ‘실제로 동작 중’이라는 상태를 구별하는 것을 제안한다. 예를 들어 스케줄러가 ON이어도 연결 실패로 실행할 수 없다면 그 이유를 표시한다. 서버 연결이 끊겨 현재 상태를 알 수 없을 때는 마지막 상태를 실시간 상태처럼 표시하지 않는다.

캐릭터의 기동·정지가 스케줄러만을 뜻하는지, 수동 입력 응답까지 포함한 방 전체의 실행 상태인지 확정해야 한다. 기본 제안은 스케줄러 OFF가 자동 일상 대화만 중지하고 사용자의 직접 채팅은 허용하는 것이다. 방 전체 일시정지와는 별개의 제어로 검토한다.

## 채팅: 앱 안에서 실시간 대화

선택한 방의 저장된 대화를 불러오고 입력창에서 메시지를 전송한다. 응답과 처리 상태는 화면에 실시간으로 갱신한다. 토큰 단위 스트리밍 여부는 별도 선택이며, 실시간 채팅 요구만으로 확정하지 않는다.

대화 입력과 응답은 기존 방의 기록·컨텍스트·기억을 사용하고 영구 저장한다. 화면을 닫거나 다른 방으로 이동해도 기록을 유지하며, 재접속 시 저장된 기록과 현재 처리 상태를 다시 조회하는 방식을 제안한다. 전송 중·응답 생성 중·실패 상태를 구별하고 실패를 정상 응답처럼 표시하지 않는다.

자체 UI가 새 입력 경로가 되므로 아래 계약은 추가 설계가 필요하다.

- 자체 UI와 외부 메신저에서 같은 방에 동시에 입력할 때의 처리 순서와 중복 방지.
- 앱에서 보낸 메시지·응답을 외부 메신저에도 전송할지, 각 입력 경로로만 응답할지.
- 외부 메신저에서 발생한 대화와 전송 상태를 앱 화면에 갱신하는 방법.
- 재접속·재전송 시 같은 입력을 두 번 저장하거나 모델을 중복 호출하지 않는 방법.

공통 방 기록을 조회하는 것과 외부 메신저에 메시지를 복제 전송하는 것은 별개다. 복제 전송 정책은 아직 정하지 않는다.

## 우측 패널: 현재 방 설정

채팅 화면에서 설정을 열면 우측 패널을 표시하고 닫으면 채팅 화면으로 돌아간다. 좁은 화면에서의 패널 표현은 후속 반응형 설계에서 정한다.

| 설정 묶음 | 내용 |
| --- | --- |
| 일상 대화 스케줄러 | 방별 ON/OFF, 상태와 예약 확인. 세부 주기·시간대·조용한 시간 설정은 실행 정책과 함께 검토 |
| 방 정보 | 방 이름 등 해당 대화 프로필의 정보 |
| 캐릭터·내 페르소나 | 방에 복사된 컨텍스트 직접 편집 |
| 모델·프롬프트 | 모델 연결 선택, 방별 생성 옵션과 지시 내용 |
| 메신저 연결 | 해당 방의 외부 대화 위치와 연결 상태 |
| 방 삭제 | 해당 방의 기록·기억 등 삭제 범위를 안내하고 실행 |

편집은 현재 방에 적용되며 캐릭터 원본이나 다른 방에 자동 반영하지 않는다. 공용 연결 자체의 수정은 좌측 연결 설정에서 영향받는 방을 확인하도록 제안한다. 저장 완료·실패·충돌을 구별하고, 스케줄러 토글도 서버에 저장·적용된 결과를 표시한다.

스케줄러 ON/OFF 선택은 재시작 후 유지해야 한다. [실행 방식 결정](결정/002-로컬서버-웹UI.md)에 따라 스케줄러는 백엔드가 담당하며 브라우저를 닫아도 서버가 실행 중이면 계속 동작한다. 서버 종료 중 놓친 일정 처리와 OFF 시 이미 실행 중인 작업 처리 방식은 별도 계약으로 확정한다.

## 기존 설계와의 연결 및 남은 선택

기존 자체 채팅은 선택 사항이었으나 이번 구상에는 앱 내 실시간 채팅이 포함된다. 스케줄러 제어도 UI 요구에 포함하되, 일상 대화 생성 규칙과 구현 순서는 아직 확정하지 않는다.

데이터 ERD에는 자체 UI 입력의 식별·중복 방지·응답 전달 경로와 방별 스케줄러 전체 활성 설정을 추가 검토해야 한다. 기존 개별 예약의 `SCHEDULED_ACTION.enabled`와 방 전체의 스케줄러 ON/OFF는 범위가 다르므로 동일 필드로 간주하지 않는다. 현재 문서 등록만으로 ERD의 세부 필드가 확정된 것은 아니다.

구현 방식의 결정 원본은 [로컬 서버와 로컬 웹 UI 채택](결정/002-로컬서버-웹UI.md)이다. 사용자 PC의 서버와 같은 PC의 브라우저를 기본 구성으로 삼는다. 세부 UI 기술 선택에는 다음 기준을 검토한다.

- 채팅과 상태 갱신, 긴 컨텍스트 편집, 우측 패널을 구현하기 적합한지.
- 기존 Python 백엔드와의 통신·인증 및 배포·업데이트 방법.
- 스케줄러를 실행할 서버 또는 백그라운드 프로세스의 수명.
- 데스크톱·모바일 지원 범위와 유지보수 부담.

프런트엔드 프레임워크, 컴포넌트 라이브러리, 백엔드 웹 프레임워크와 실시간 통신 방식은 미정이다. 트레이와 설치형 앱은 후속 확장 후보다. 구체적인 기술 비교와 채택은 후속 논의에서 수행한다.
