# 외부 라이브러리와 내부 연결 저장 구조 검토안

작성일: 2026-09-17

이 문서는 저장 구조에 관한 추가 대화를 재검토한 **후속 검토용 제안**이다. 지금 승인하거나 구현할 필요는 없다. 사용자 요구, 제안, 미결정을 구분해 추후 설계 검토를 재개할 수 있도록 남긴다. 실행 코드·DB·마이그레이션을 변경한 문서가 아니며, 현재 구현의 다중 OS 동작이나 영구 저장을 검증했다는 의미도 아니다.

기존 [기초 설계](기초설계.md)는 방의 독립성·편집·삭제·재시작 요구의 원본이고, [데이터 ERD](데이터설계.md)는 기존 논리 데이터 구조의 원본이다. 이 문서는 그 구조의 **저장 위치와 공유 경계를 변경하는 검토안**이다. 채택 전까지 기존 ERD를 대체하지 않는다. 작업 상태와 일정은 [프로젝트 문서](프로젝트.md#작업-목록)에서만 관리한다.

## 1. 다음 검토 때 먼저 읽을 내용

- 사용자 요구: 프로그램 설치 위치와 데이터 위치를 분리하고, 모델·메신저 연결은 앱 내부에, 페르소나·대화방 등 콘텐츠는 사용자가 지정한 외부 위치에 보관한다.
- 제안: 내부 `system.db`와 외부 라이브러리를 분리한다. 페르소나·프롬프트는 텍스트 파일, 대화방은 폴더 하나로 묶는다.
- 후보: 방 폴더 안의 메시지·기억·상태는 방별 SQLite로 관리한다. 외부 저장이라고 반드시 모든 데이터를 JSON으로 저장할 필요는 없다.
- 주요 비용: 여러 DB와 파일의 일관성, 방별 마이그레이션, 삭제·이동·내보내기 중 종료에 대한 복구가 필요하다.
- 핵심 미결정: 방별 DB 채택, 방 컨텍스트의 파일/DB 원본 선택, 공유와 백업의 포함 범위다.

## 2. 요구사항과 제안을 구분

| 구분 | 내용 |
| --- | --- |
| 사용자가 요청한 방향 | 다른 OS에서도 사용할 수 있는 구조, 설치 위치와 데이터 저장 위치의 분리 및 지정 |
| 사용자가 요청한 방향 | 모델 연결·채팅 앱 연결은 앱 내부 저장 |
| 사용자가 요청한 방향 | 페르소나·대화방 및 커스텀 콘텐츠는 외부 저장, 공유하기 쉬운 구성 |
| 유지할 기존 요구 | 같은 캐릭터로 여러 독립 방 생성, 방 안에서 컨텍스트 직접 수정, 방 재개, 재시작 보존, 방 소유 데이터 삭제 |
| 구현 제안 | 내부 SQLite + 외부 폴더, Markdown과 구조화 메타데이터의 조합 |
| 구현 제안 | 방별 SQLite, UUID 기반 연결, 공유 패키지, 원본 프로파일의 방별 사본 |
| 아직 미결정 | YAML/JSON 선택, 파일 직접 편집 지원 범위, 전용 확장자, 백업·동기화 정책, OS 비밀 저장소 구현 |

여기서 ‘앱 내부’는 실행 파일이나 설치 폴더 안을 뜻하지 않는다. OS별 앱 전용 데이터 디렉터리를 뜻한다. ‘외부’는 앱 전용 디렉터리 밖의 사용자 지정 라이브러리를 뜻하며, 인터넷 업로드·클라우드·NAS를 전제하지 않는다.

## 3. 저장 영역과 원본 소유권

| 영역 | 보관할 원본 | 다른 장치로 공유할 때 |
| --- | --- | --- |
| 설치 디렉터리 | 실행 코드, 기본 리소스, 마이그레이션 정의 | 앱 설치·업데이트로 공급 |
| 부트스트랩 설정 | 내부 데이터 경로와 라이브러리 경로 등 시작에 필요한 최소 설정 | 장치별 경로이므로 공유 콘텐츠에서 제외 |
| 내부 `system.db` | 모델·메신저 연결, 허용 계정, 연결 선택, 외부 채팅 주소, 수신 커서·라우팅 상태 | 콘텐츠 공유에서 제외하고 새 환경에서 재연결 |
| 보호된 비밀 저장소 | API 키·봇 토큰 | 별도 복구 대상. DB에 참조가 있다고 다른 OS에서 키까지 복구되지는 않음 |
| 외부 프로파일·템플릿 | 개인 페르소나, 캐릭터, 초기 관계, 프롬프트, 재사용 생성 옵션 | 폴더 또는 패키지로 이동·공유 |
| 외부 방 | 방 메타데이터·컨텍스트 사본·메시지·기억·상태·일정·에셋 | 선택한 범위로 내보내기. 연결은 비활성 상태로 가져오기 |
| 로컬 인덱스·캐시 | 외부 라이브러리에서 다시 만들 수 있는 목록·검색 결과 | 원본이 아니므로 재구성 가능 |

내부 DB에 외부 프로파일 전체를 별도 원본으로 복제하지 않는다. 목록 표시를 위한 캐시는 파일의 ID·버전·해시와 대응시키며 라이브러리에서 다시 만들 수 있어야 한다. 라이브러리 경로의 원본은 부트스트랩 설정 한 곳에 둔다.

모델 설정은 연결과 콘텐츠로 나눈다. 엔드포인트·인증·로컬 서버 경로는 내부 연결이다. 모델 식별자·생성 옵션·프롬프트는 외부에 보관할 수 있는 재현 정보다. 공유된 모델명이 다른 공급자에서도 실행 가능함을 보장하지 않으며, 가져올 때 선택한 연결의 지원 옵션을 재검증한다.

## 4. 폴더 구성 후보

다음 이름과 형식은 예시다. 확장자·제품 이름·최종 경로는 아직 확정하지 않는다.

```text
OS 앱 설정 위치/
└── bootstrap.json             # 내부 데이터 위치, 라이브러리 위치

OS 앱 데이터 위치/
├── system.db                  # 연결, 장치별 바인딩, 운영 상태
├── cache/                     # 재구성 가능한 색인
└── logs/                      # 비밀값·대화 원문을 기록하지 않음

사용자 지정 라이브러리/
├── library.json               # 라이브러리 ID와 형식 버전
├── personas/<id>/
│   ├── profile.json           # ID, 이름, 형식 버전, 텍스트 참조
│   ├── persona.md
│   └── assets/
├── characters/<id>/
│   ├── profile.json
│   ├── persona.md
│   ├── relationship.md        # 초기 관계 설정
│   └── assets/
├── templates/<id>/
│   ├── template.json
│   └── prompt.md
└── rooms/<id>/
    ├── manifest.json          # 방 ID, 패키지 형식 등 식별 정보
    ├── conversation.db        # 방 운영 데이터의 원본 후보
    ├── context/               # 검토안에 따라 사본 또는 편집용 파일
    └── assets/                # 이 방이 자체 소유하는 파일
```

JSON은 Python 표준 라이브러리만으로 다룰 수 있어 초기 후보로 제안한다. YAML은 주석·수동 편집의 편의성이 있지만 별도 파서와 안전한 데이터 로딩 정책이 필요하다. 어느 형식이든 긴 자연어는 Markdown으로 분리하고, 구조화 필드는 스키마 검증한다. 파일별 형식 버전과 DB 마이그레이션 버전은 별도로 관리한다.

프로파일의 여러 파일을 함께 수정할 때도 중간 저장 상태가 노출될 수 있다. 앱 저장은 임시 영역에서 전체 내용을 검증한 뒤 게시하며, 직접 편집을 지원한다면 명시적인 다시 불러오기와 변경 충돌 처리가 필요하다. 파일 감지만으로 작성 중인 내용을 즉시 대화에 적용하지 않는다.

## 5. 대화방 저장 방식 비교

| 후보 | 이점 | 부담 | 이번 검토의 판단 |
| --- | --- | --- | --- |
| 방별 JSON/JSONL·Markdown | 일반 편집기로 열기 쉽고 텍스트 비교·공유가 편함 | 검색·수정 이력·중복 방지·여러 파일의 저장 일관성을 직접 구현 | 내보내기 형식에는 적합. 운영 원본 채택은 추가 검토 |
| 라이브러리 전체 SQLite 하나 | 방 간 조회·마이그레이션·트랜잭션 관리가 간단 | 방 하나를 공유할 때 추출 절차 필요, 폴더 단위 독립성이 낮음 | 구현 단순성을 우선할 때 대안 |
| 방별 SQLite + 에셋 폴더 | 방별 격리와 이동·공유가 자연스러움, 방 내부 트랜잭션 사용 가능 | 여러 DB의 버전·연결·전역 검색·운영 복구 관리가 늘어남 | 사용자 요구에 맞는 우선 검토 후보, 아직 채택 아님 |

텍스트 파일도 원자적 교체·저널·잠금 등을 설계하면 안전하게 저장할 수 있다. 앞선 대화의 ‘파일은 손상되고 DB는 안전하다’는 식의 단순 비교 대신 구현 비용과 필요한 작업을 비교한다. SQLite도 파일·설정·운영 방식에 따라 별도 백업과 복구가 필요하다.

## 6. 방 컨텍스트와 데이터 원본의 중복 방지

방 생성 시 개인·캐릭터 프로파일과 프롬프트를 복사한다. 기존 방은 해당 사본을 사용하고 원본 변경을 자동 적용하지 않는다. 출처 ID·버전은 설명용이며 원본이 없어져도 방을 열 수 있어야 한다. 프로파일 에셋도 방으로 복사하는 안을 우선 제안해 폴더 자체의 독립성을 확보한다. 중복 파일을 줄이는 공용 에셋 저장소는 후속 최적화다.

앞선 제안에는 `room.yaml`, `context/*.md`, 방 DB의 설정 사본이 함께 등장했다. 같은 내용을 모두 원본으로 두면 어떤 수정이 최신인지 불명확해진다. 다음 두 방식 중 하나를 선택해야 한다.

| 선택 | 저장 원본 | 편집 처리 |
| --- | --- | --- |
| A. DB 원본 | 이름·설정·컨텍스트·버전을 방 DB에서 관리 | `context/`는 내보내기·편집용 사본. 수정 파일은 가져오기 검증 후 새 revision으로 반영 |
| B. 파일 원본 | 버전별 컨텍스트 파일, DB에는 적용 버전·해시·메시지 관계 저장 | 완성된 파일 버전을 먼저 기록한 뒤 DB가 활성 버전을 가리킴. 실패 시 미사용 파일 정리·누락 복구 필요 |

초기 구현에는 A를 제안한다. 사용자 요구는 외부 저장과 공유이며, 방의 모든 필드를 외부 편집기에서 즉시 수정하는 기능까지 필수라고 확인되지는 않았다. 페르소나 원본은 파일로 편집 가능하게 하고, 방 컨텍스트는 UI 또는 명시적 가져오기로 변경할 수 있다. 직접 파일 편집이 핵심 요구로 확인되면 B를 선택한다.

`manifest.json`에는 형식·ID 등 식별 정보만 두고 현재 방 이름·활성 revision을 DB와 중복 저장하지 않는다. 식별 정보가 서로 다르면 자동 덮어쓰기 대신 불일치로 표시한다.

## 7. 내부 연결과 외부 방의 결합

내부에는 외부 방을 찾는 레지스트리와 장치별 실행 연결을 둔다. 후보 키는 `(library_id, room_id)`이며, 폴더 이름이나 표시 이름을 식별자로 사용하지 않는다.

| 내부 데이터 후보 | 책임 |
| --- | --- |
| `ROOM_REGISTRY` | 라이브러리 ID·방 ID·라이브러리 기준 상대 경로·가용 상태. 목록 정보는 재구성 가능 |
| `ROOM_RUNTIME_BINDING` | 로컬 모델 연결 선택·연결 revision·라우팅 generation |
| 기존 `CHANNEL_BINDING` | 메신저 연결·허용 계정·외부 채팅/토픽·활성화 경계 |
| 수신·전송 운영 기록 | 공급자 이벤트 식별자, 중복 방지, 커서와 송신 결과 관리. 방별로 제거 가능하게 소속 표시 |
| 삭제·이동 작업 기록 | 라이브러리 접근 실패나 중간 종료 후에도 정리를 재개할 최소 상태 |

실제 모델 요청의 비밀값 없는 모델·옵션 사본은 방의 턴에 남긴다. API 키·봇 토큰·실제 라우팅 주소는 공유 방의 실행 설정으로 넣지 않는다. 연결 없이 가져온 방도 기록과 컨텍스트를 읽고 편집할 수 있어야 한다.

내부 DB와 방 DB 사이에는 SQLite 외래 키를 걸 수 없다. 각 DB 내부의 소유 관계에는 FK·고유 제약을 사용하고, 저장소 사이의 참조는 애플리케이션에서 확인한다. 라이브러리가 연결되지 않거나 경로가 없으면 ‘접근 불가’로 표시하고 빈 DB를 자동 생성하지 않는다. [SQLite 외래 키 제한](https://sqlite.org/foreignkeys.html#limits)

## 8. 기존 ERD에 필요한 변경

아래는 변경 영향만 정리한 것으로, 기존 테이블 정의를 복제한 새로운 ERD가 아니다.

| 기존 대상 | 분리 시 변경 |
| --- | --- |
| `USER_PERSONA`, `CHARACTER_PROFILE`, `PROMPT_TEMPLATE` | 파일 원본으로 전환. 내부 레지스트리는 재구성 가능한 색인 |
| `MODEL_PRESET` | 내부 연결 선택과 외부로 공유 가능한 모델·옵션 프리셋을 분리 검토 |
| `ROOM`, `ROOM_REVISION`, `ROOM_PROMPT` | 방 DB로 이동하는 후보. 컨텍스트 A/B 선택에 따라 사본 위치 확정 |
| 원본 페르소나·프롬프트에 대한 FK | 파일의 ID·버전 출처로 변경. 자동 `SET NULL`이나 DB FK 검사를 기대하지 않음 |
| `ROOM_REVISION.model_connection_id` | 내부 실행 바인딩으로 분리. 과거 실행의 비밀값 없는 정보만 방에 보존 |
| `MESSAGE`, `TURN`, 기억·상태·사건·일정 | 방 DB에 소속. 방 내부 FK와 데이터 격리 유지 |
| `CHANNEL_BINDING`, `INBOUND_RECEIPT`, `DELIVERY` | 연결·외부 주소는 내부에, 메시지 본문은 방에 저장하는 경계 재설계. 기존 복합 FK를 그대로 옮길 수 없음 |
| `CLEANUP_JOB` | 방 DB를 제거한 뒤에도 남아 복구할 수 있도록 내부 DB에 작업 상태 보관 |
| `ASSET`·프로파일/방 에셋 참조 | 각 패키지의 상대 경로·체크섬과 소유권으로 재설계 |

분리된 저장소 전체에 기존 단일 DB의 `ON DELETE CASCADE`나 단일 트랜잭션을 적용할 수 없다. 기존 ERD의 의미상 관계와 물리 FK를 구분한 후 새 물리 설계를 작성해야 한다.

## 9. 저장·재시작·이동·삭제 계약

### 저장과 수신

사용자에게 저장 성공을 알리기 전에 해당 원본의 영구 저장을 완료한다. 모델 호출 도중 DB 트랜잭션을 오래 유지하지 않는다. 내부 DB와 방 DB의 변경은 하나의 원자적 커밋이라고 가정하지 않는다.

수신 경로는 내부의 이벤트 식별·방 배정 기록과 방 DB의 메시지 저장을 같은 작업 ID로 연결하는 방안을 검토한다. 방 메시지가 저장된 뒤 수신 완료·커서를 확정한다. 중간 종료 후 같은 이벤트가 다시 와도 같은 방·같은 작업으로 복구하고 다른 방에 재배정하지 않아야 한다. 정확한 중복 키와 재수신 불가능 구간은 메신저별 물리 설계에서 확인한다.

생성·전송 상태도 구분한다. 외부 송신 후 결과 저장 전에 종료됐다면 결과 불명 상태로 복구하고 자동 재전송하지 않는다. 라이브러리 분리로 이 기존 요구가 약해지면 안 된다.

### 이동·백업·내보내기

실행 중인 `.db` 파일 하나를 임의 복사하는 방식을 기본 공유 기능으로 삼지 않는다. WAL 사용 시 커밋된 내용이 `-wal` 파일에 남아 있을 수 있다. 앱의 내보내기는 방 변경을 잠시 정지하고 SQLite 백업 API 등으로 일관된 DB 사본을 만든 뒤, 그 사본이 참조하는 에셋을 함께 묶는 방식으로 제안한다. DB 백업만으로 여러 파일의 동일 시점까지 자동 보장되지는 않는다. [SQLite 백업](https://sqlite.org/backup.html), [WAL 파일](https://sqlite.org/wal.html#the_wal_file)

데이터 위치 변경은 새 폴더 검증 → 작업 중지 → 일관된 복사 → DB 무결성·FK·에셋 검사 → 경로 설정 전환 → 재열기 순으로 설계한다. 실패 시 기존 경로로 복구할 수 있도록 전환 상태를 기록한다. 위치 변경만으로 기존 데이터를 자동 삭제하지 않는다.

### 방 삭제

내부 바인딩을 중지하고 삭제 작업을 영구 기록한 뒤, 진행 중 생성·예약·송신을 차단하고 방 폴더와 내부의 방 전용 운영 기록·색인을 정리한다. 늦게 도착한 결과로 폴더나 방을 되살리지 않는다. 데이터 경로는 앱이 식별한 방 소유 범위만 대상으로 한다.

외장 드라이브가 빠져 있어 파일을 지울 수 없다면 삭제 완료가 아니라 정리 대기로 표시한다. 방 삭제는 공용 프로파일·연결을 지우지 않는다. 이미 만든 백업·공유 파일과 외부 메신저 기록은 별도 범위이며, 디스크의 물리적 복구 불가능한 삭제까지 보장하는 요구는 아니다.

## 10. 공유·복원·복제의 차이

| 동작 | 내용과 기본 제안 |
| --- | --- |
| 프로파일 공유 | 프로파일·설명·필수 에셋. 메시지·기억·연결 없음 |
| 방 설정 공유 | 현재 컨텍스트·비밀값 없는 생성 설정·에셋. 이력·기억·예약 실행 제외 |
| 대화 포함 공유 | 선택한 메시지·기억 등 포함 범위를 미리 표시. 대화 본문의 개인정보는 자동 제거를 보장하지 않음 |
| 개인 백업 | 방의 전체 복구 데이터. 내부 연결 설정·비밀정보 복구는 별도 보호된 절차 필요 |
| 복제 가져오기 | 새 방 ID 발급, 내부 소유 참조 재작성, 출처 ID 보존. 연결·예약 실행은 비활성 |
| 백업 복원 | 원래 ID 유지가 가능한 별도 흐름. 기존 데이터와 충돌 시 조용히 덮어쓰지 않음 |

공유 패키지는 ZIP과 형식 버전이 있는 manifest를 후보로 둔다. 전용 확장자는 후순위다. 실행용 DB를 그대로 배포하면 과거 revision이나 사용하지 않는 필드에 정보가 남을 수 있으므로, 공유 모드에서는 허용된 데이터로 새 패키지를 구성한다. 가져온 데이터는 스키마·참조·경로를 검증하며 임의 절대 경로나 상위 폴더 탈출, 패키지 안의 코드 실행을 허용하지 않는다.

## 11. OS와 파일시스템 지원 범위

OS별 기본 경로 계산과 실제 저장 로직을 분리하고, 경로 결합은 OS에 맞는 경로 API를 사용한다. 내부 데이터 위치는 OS 앱 데이터 디렉터리, 외부 라이브러리는 사용자가 지정한 디렉터리로 한다. 설치 폴더에는 사용자 데이터를 쓰지 않는 구조를 제안한다.

에셋 참조는 패키지 루트 기준 상대 경로로 저장하고, 파일명은 안정적인 ID 중심으로 구성한다. 한글 표시 이름은 메타데이터에 둔다. UTF-8, 파일명 대소문자, 예약 문자, 권한, 잠긴 파일의 이동·삭제를 Windows/macOS/Linux에서 별도로 검증해야 한다. 현재 구현이 모두 검증된 것은 아니다.

초기 지원 대상은 앱 실행 머신의 로컬 파일시스템으로 제한하는 안을 제안한다. 앞선 대화에서 NAS 경로를 예시로 든 부분은 보완이 필요하다. SQLite는 네트워크 파일시스템의 잠금·동기화 차이로 문제가 생길 수 있고 WAL은 다른 호스트의 직접 접근을 지원하지 않는다. NAS·동기화 폴더는 닫힌 백업·공유 패키지의 전달 장소로 사용하고, 여러 기기가 실행 중인 방 DB를 직접 공동 편집하는 용도로 지원하지 않는다. 원격 사용은 DB가 있는 서버의 앱 API를 통해 접근하는 별도 구조다. [네트워크 파일시스템 주의사항](https://sqlite.org/useovernet.html), [WAL 제약](https://sqlite.org/wal.html)

## 12. 나중에 검토할 순서와 확인 기준

다음은 검토 순서이며 구현 작업 상태나 승인 목록이 아니다.

1. 외부 저장의 목적을 ‘공유·백업·사용자 소유’로 충족할지, ‘방의 모든 데이터를 직접 파일 편집’까지 제공할지 확인한다.
2. 방별 DB와 라이브러리 전체 DB 중 하나를 선택하고, 방 컨텍스트 A/B를 결정한다.
3. 공유·개인 백업·복제·복원의 포함 데이터와 ID 정책을 정한다.
4. 수정된 저장 경계에 맞춰 ERD의 FK·중복 방지·커서·전송 기록·삭제 복구를 재설계한다.
5. 파일 형식과 버전, OS 경로, 마이그레이션·복구 시나리오를 정한 뒤 구현 범위를 나눈다.

추후 확인할 결과:

- 프로파일 폴더만 가져와도 새 방을 만들 수 있다.
- 동일 원본으로 만든 두 방의 컨텍스트·메시지·기억이 독립적이다.
- 원본 프로파일 삭제 후에도 기존 방과 에셋을 읽을 수 있다.
- 다른 OS로 옮긴 방을 연결 없이 열 수 있고, 새 연결을 선택한 뒤 계속 대화할 수 있다.
- 라이브러리 누락·손상·중복 ID가 빈 데이터 생성이나 자동 덮어쓰기로 처리되지 않는다.
- 저장·수신·송신·이동·삭제 중 종료해도 재시작 후 누락과 중복을 식별·복구한다.
- 가져온 예약은 자동 실행되지 않으며, 공유 파일에 연결 비밀값과 실행 주소가 포함되지 않는다.
- 실행 중 내보낸 사본의 DB와 에셋 참조가 일치한다.
