# 방 중심 백엔드 구현 설계와 변경 기록

백엔드를 수정할 때 함께 갱신하는 구현 계약의 원본이다. 사용자 요구는 [기초 설계](기초설계.md), 실행 형태는 [로컬 서버 결정](결정/002-로컬서버-웹UI.md), 상태·검증 결과·구현 순서는 [프로젝트 문서](프로젝트.md#작업-목록)에서 관리한다. 이 문서에는 책임·호출 계약과 변경 이유를 남기고 작업 상태를 중복 관리하지 않는다.

## 구현 순서의 정정

연결 정의와 방 실행을 분리하는 B01 이후에는 [저장 배치 결정](결정/003-내부연결DB-외부방별SQLite.md)에 맞게 저장 계약을 정리하고 실제 저장소를 연결한다. 기존의 ‘B02 메신저 전환 후 영구 저장’ 순서는 웹 MVP를 지연하므로 변경한다. B02는 웹 MVP 다음에 I06과 함께 진행한다. 구체적인 순서와 상태는 [프로젝트 문서](프로젝트.md#구현-순서)를 따른다. 메모리 어댑터는 구조 검증용이며 영구 저장 요구를 충족하지 않는다.

| 저장소 포트 | 방 revision·입력 중복·결과 반영의 원자적 계약 | 특정 파일/DB 배치 |
| 조립 지점 | 저장소·비밀 공급자·실행 어댑터 주입과 종료 | 도메인 처리 규칙 |

기존 `ChatModel`과 LM Studio 어댑터를 재사용한다. 새로운 방 실행 서비스는 SDK에 의존하지 않는다. HTTP 클라이언트는 백엔드 수명 동안 공유하고 매 호출의 모델 설정은 방별로 구성한다. 연결 정의에 원문 키를 담지 않고 실행 직전에 비밀 공급자에서 조회한다. 주소·파라미터 검증은 기존 LM Studio 설정 검증을 재사용한다.

## 현재 구현의 처리 계약

1. 생성한 방 ID는 외부 주소와 독립적이며 재사용하지 않는다. 방의 컨텍스트는 불변 사본으로 전달한다.
2. `create()`는 연결 없는 방을 만들고 공통 타입·유한성을 검사한다. `bind()`는 예상 방 revision과 바인딩 generation을 확인한 뒤 공급자·주소·허용 범위를 비밀 조회·HTTP 요청 없이 검증한다. 연결된 방의 모델 옵션 변경에도 공급자 검증을 적용하고, 실패한 변경은 기존 설정을 유지한다. 모델 설정이 같은 이름·컨텍스트 편집은 연결이 비활성이어도 가능하다. 실행 직전에도 공급자 설정을 검증하며 미연결 방은 실행을 거부한다. 미연결 콘텐츠 저장 성공은 해당 모델 실행 가능 판정을 뜻하지 않는다.
3. 수정에는 예상 revision이 필요하다. 실제 변경 시 revision을 증가시키고 오래된 편집을 거부한다.
4. 입력 중복 키는 내부 접수표의 `(source, request_id)`다. source는 인증·라우팅 경계에서 정하며 외부 입력값을 권한 근거로 사용하지 않는다. 접수표가 있는 동안 같은 외부 요청의 다른 방 재할당을 거부한다. 방 저장소는 불투명 input ID로 중복과 다른 본문 충돌을 검사한다. 웹 호출자도 출처별로 고유한 요청 키를 발급하고 재요청에만 같은 키를 써야 한다.
5. 한 방의 입력은 순서대로 처리하되 다른 방은 독립적으로 실행할 수 있다. 입력을 접수한 뒤 모델을 호출한다. 오류·취소를 접수 기록에서 구분하며 동일 키를 자동 재호출하지 않는다.
6. 호출 중 방 수정·삭제 또는 연결 수정·비활성화가 발생하면 늦은 결과를 대화에 반영하지 않는다. 바인딩 generation은 해제나 같은 연결 재지정 때도 증가하므로 다른 연결로 바꿨다가 되돌린 결과도 폐기한다. 한 서비스 안의 방 편집·바인딩 변경·삭제·결과 확정은 짧은 방별 변경 잠금을 공유한다. 모델 I/O는 이 잠금 밖에서 수행한다. 공용 연결 편집과 여러 DB의 원자적 결과 반영·다중 실행자는 영구 저장 단계에서 별도로 강화해야 한다.
7. 생성 결과 기록과 외부 송신은 분리한다. 새 실행 서비스는 생성 결과를 반환하며 실제 메신저 송신과 전송 결과 저장은 B02/I06에서 연결한다. 실패한 입력은 접수 기록에 남고 성공한 턴만 현재 모델의 대화 이력에 포함하는 초기 정책을 사용한다.
8. 방 삭제는 해당 방의 입력·이력·내부 바인딩·접수표를 제거한다. 늦은 호출로 방을 새로 만들지 않는다. 파일·DB 삭제 복구는 영구 저장 단계에서 추가한다. 접수표 삭제 후 같은 외부 경로를 다른 방에 재연결했을 때 과거 이벤트를 차단하는 수신 커서·활성화 경계는 B02/I06에서 구현해야 한다. 현재 메모리 라우터만으로 이 재연결 시나리오를 안전하게 운영할 수는 없다.

기존 `run` CLI와 `ConversationService`는 Discord 연결 검증용 경로로 보존한다. 새 방 서비스·명시적 라우터·조립 함수를 먼저 작성하고 검증한 뒤 B02에서 기존 수신 경로를 전환한다. 인증되지 않은 첫 메시지로 방을 자동 생성하는 우회 구현을 도입하지 않는다.

모델 연결 정의·방 설정·실행 자원의 분리는 우선 구현하지만, 메신저 SDK 수신 작업의 공유·중지·재연결과 진행 중 전송은 별도 전환 단계에서 다룬다. 내부 운영 데이터는 SQLite 어댑터를 선택해 보존할 수 있다. 루프백 HTTP 서버·웹 API·스케줄러와 방 대화의 영구 저장은 아직 실행 경로에 포함하지 않는다.

검증용 메모리 구현은 단일 이벤트 루프·단일 `RoomService` 실행자를 전제로 한다. 대화 이력과 입력 상태를 프로세스 메모리에 보관하며 데이터 용량·모델 컨텍스트 예산·영구 중복 방지·다중 실행자 잠금은 제품용 저장/실행 단계에서 보완한다. 메신저 정의는 자료형만 제공하며 활성 연결 관리와 메신저 경로의 generation은 B02 범위다. 모델 실행 바인딩의 generation은 현재 `RoomBindings` 구현에서 관리한다. 조립 함수 호출자는 진행 중 요청을 종료한 후 컨텍스트를 닫아야 하며, 서버 종료 시 요청 취소·대기는 실제 서버 수명 관리에서 구현한다.

## 영구 저장 전 코드 전환 설계

물리 필드·원본 소유권·DB 간 복구는 [현재 데이터 설계](데이터설계.md)를 따른다. `RoomModelConfig`·`RoomRuntimeBinding`과 미연결 콘텐츠 CRUD, 내부 입력 접수표와 방 입력은 아래처럼 분리했다. 방 DB 스키마·영구 삭제·복구는 남은 전환이므로 현재 메모리 객체를 그대로 방 SQLite 스키마로 간주하지 않는다.

| 전환 대상 | 계약 | 검증할 결과 |
| --- | --- | --- |
| `Room.model`의 연결 ID 제거 | `RoomModelConfig`에는 모델 ID·옵션만, 별도 `RoomBindings` 포트에 내부 `RoomRuntimeBinding` 저장. 실행 시 `ModelSelection` 조립 | 방 콘텐츠의 직렬화 결과에 연결 ID·주소·비밀 참조가 없음 |
| 콘텐츠 CRUD와 실행 연결 검증 | 방 생성/조회/편집은 미연결 상태도 허용. 연결 지정·해제는 `bind()`로 분리 | 연결 선택·연결된 모델 옵션 변경·응답 실행에는 공급자 검증. 실패한 수정은 기존 설정 보존 |
| 외부 식별자가 있는 `RoomInput` 실행 명령 | `InputReceipts`에 외부 출처·요청 키, `RoomStore`에는 `StoredRoomInput`과 `RoomTurn`만 전달 | 접수표 유지 중 다른 방 재배정 차단, 방 턴 직렬화에 외부 ID 없음. 삭제 후 재연결 차단은 별도 수신 계약 필요 |
| 모델 호출의 방 잠금만 존재 | 설정·연결 변경과 결과 확정을 조정하는 방별 실행 경계 | 연결 변경 직후 오래된 결과를 저장하지 않음. 모델 I/O 동안 DB 트랜잭션을 붙잡지 않음 |
| `RoomStore.delete()`가 메모리 기록 즉시 제거 | 내부 삭제 작업 기록과 외부 방 소유 자원의 재시작 가능한 정리 | 파일 접근 실패는 삭제 완료가 아님. 공용 연결·프로파일·다른 방 보존 |
| 현재 이력과 입력 상태가 메모리에만 존재 | 영구 입력/턴 저장과 최근 대화 조회를 분리 | 전체 기록 보존과 모델 컨텍스트 예산이 다른 책임임을 검증 |

호출자는 `RoomService`와 `room_backend()`에 `RoomBindings`와 `InputReceipts`를 주입하고, 생성/수정에는 `ModelSelection` 대신 `RoomModelConfig`를 전달해야 한다. 생성 후 `bind(room.id, room.revision, 0, connection_id)`로 연결한다. 생성과 연결 지정은 독립 작업이며 연결 실패 시 미연결 방은 보존한다. 바인딩만 변경하면 방 revision과 이력은 바뀌지 않는다. `respond()`는 기존 `RoomInput` 명령을 받지만 반환하는 턴의 `input`은 `StoredRoomInput`이다. 이 변경은 새 방 API의 계약 변경이며 기존 Discord CLI 경로에는 영향이 없다.

`InMemoryRoomBindings`와 `InMemoryInputReceipts`는 다른 메모리 어댑터와 마찬가지로 재시작 보존을 제공하지 않는다. 현재 범위는 단일 라이브러리를 다루는 단일 서비스 인스턴스다. 여러 라이브러리의 복합 식별과 저장소 간 삭제 실패·중단 복구는 영구 구현에서 추가한다. 현재 방 삭제 뒤 바인딩·접수표를 제거하는 순차 호출을 DB 전체의 원자적 삭제 계약으로 해석하지 않는다.

### 입력 접수의 실패 경계

`reserve()`로 내부 ID와 대상 방을 고정 → 방 입력을 저장 → `mark_accepted()`로 내부 접수 확정 → 모델 실행 순서다. 내부 접수표에는 본문을 복사하지 않으며, `accepted`는 모델 성공 여부가 아니라 방 입력 저장 확인 여부다. 모델 실행 상태는 방의 `RoomTurn`이 소유한다.

- 예약이나 방 저장이 실패하면 예외를 반환하고 모델을 호출하지 않는다. 방 본문이 저장되기 전의 예약은 본문 접수 성공을 뜻하지 않는다. 재전송 시 같은 예약 ID를 사용한다.
- 방 기록은 남았지만 접수 확정이 실패하거나 저장 결과가 불명확하면 재요청에서 기존 `pending` 턴을 반환하고 모델을 자동 재실행하지 않는다. 현재는 진행 작업이 없는 `pending`도 가능하다. 재시작 후 중단 상태 전환·명시적 재시도 API는 영구 저장 단계에서 추가한다.
- 이미 확정된 receipt의 방 입력이 없으면 `allow_new=False`로 복원·신규 생성을 거부한다. receipt만으로 본문 복구를 성공 처리하지 않는다.
- 본문 변경 충돌은 방 저장소에서 검사한다. 내부 출처·요청 키를 방 저장소로 전달하거나 예외 메시지에 출력하지 않는다.

연결 없는 방의 콘텐츠 편집을 허용하는 계약은 기존 저장 전 검증을 제거하는 것이 아니다. 숫자 타입·유한성 같은 공통 검증은 항상 수행하고, 실행 연결을 지정할 때 공급자별 설정을 검증한다. 실행 직전에도 최신 연결을 재검증한다. 연결되지 않은 콘텐츠에 ‘실행 가능한 설정’이라는 상태를 부여하지 않는다.

첫 전환 테스트는 두 방의 독립성, 한 방의 연결만 변경, 미연결 방의 조회·편집과 실행 거부, 내부 식별자의 외부 저장 제외를 검증한다. 실제 저장 어댑터 단계에서는 파일 재열기, 중단된 입력·삭제 복구, 라이브러리 누락·손상과 schema version 불일치를 추가한다. 테스트 상태는 프로젝트 작업 원본에만 기록한다.

## 내부 운영 SQLite 어댑터

`SqliteRuntimeDatabase`는 기존 `ModelConnections`·`RoomBindings`·`InputReceipts` 포트를 구현하는 세 객체를 제공한다. Python 표준 `sqlite3`를 사용하며 추가 DB 프레임워크는 도입하지 않는다. 단일 라이브러리 범위의 내부 데이터만 다루고, 실제 스키마와 남은 registry 관계는 [현재 데이터 설계](데이터설계.md#내부-sqlite-v1의-실제-범위)를 따른다.

### 파일과 실패 처리

- `await SqliteRuntimeDatabase.create(path)`는 새 파일 전용이다. 부모 디렉터리를 자동 생성하지 않고, 기존 파일을 덮어쓰지 않는다. 파일 선점 후 스키마·식별자·버전을 한 트랜잭션으로 초기화한다. 초기화 중 오류나 종료로 빈/미완성 파일이 남을 수 있으며 이를 자동 삭제하거나 완성된 DB로 처리하지 않는다.
- `await SqliteRuntimeDatabase.open(path)`는 `mode=rw`로 기존 파일만 연다. 누락·다른 DB 종류·미지원 버전·손상·참조 무결성 오류를 거부한다. v1만 지원하며 자동 업그레이드나 다운그레이드를 하지 않는다. DB를 연 이후에도 작업마다 버전·고유 식별자를 확인해 파일 교체를 감지한다.
- DB 오류·잠김·접근 실패는 원문 SQL 오류·개인 경로를 담지 않는 `StorageUnavailable`로 전달한다. 실패를 메모리 저장 성공으로 바꾸지 않는다. API 키·봇 토큰 저장 API는 제공하지 않으며 `secret_ref`만 받는다. DB 암호화나 OS 비밀 저장을 구현한 것은 아니다. 호출자는 개인 데이터 영역과 적절한 파일 접근 권한을 준비해야 한다.

### 트랜잭션과 취소

조회는 읽기 트랜잭션, 변경은 `BEGIN IMMEDIATE` 안에서 검사·갱신·커밋한다. 연결 revision, 바인딩 generation, `(source, request_id)` 예약은 같은 DB를 연 다른 어댑터 객체와도 원자적으로 충돌을 검사한다. 외부 값을 SQL 문자열에 보간하지 않는다. 모델 연결 FK를 활성화하고 DB 연결은 매 작업 후 닫는다.

파일·SQLite 작업은 작업 스레드에서 처리한다. 호출 취소 시 실행 중인 스레드의 커밋/롤백과 자원 정리가 끝난 뒤 `CancelledError`를 전달한다. 이를 통해 호출자의 방 변경 잠금이 DB 작업 완료 전에 풀리지 않게 한다. 취소는 롤백 보장이 아니므로 호출자는 결과 불명 상태로 취급해야 한다. 종료 시에는 서비스 요청을 먼저 취소·대기한 뒤 이벤트 루프를 닫아야 한다. 모델 I/O 중 SQLite 트랜잭션을 유지하지 않는다.

내부 DB만의 CAS 검증은 여러 프로세스가 하나의 방 응답을 동시에 실행해도 안전하다는 뜻이 아니다. 방 직렬화, 공용 연결 편집과 외부 방 결과 반영의 조정, 여러 DB 삭제·복구는 별도 구현이 필요하다.

### 조립과 제한

호출자가 정한 개인 DB 경로를 기존 저장소로 열고 다음처럼 주입한다. 최초 생성은 명시적으로 `create(path)`를 호출하며 `open()` 실패 시 자동으로 `create()`를 호출하지 않는다. `rooms`와 `secrets`는 호출자가 제공하는 기존 포트 구현이다.

```python
runtime = await SqliteRuntimeDatabase.open(path)
async with room_backend(
    rooms, runtime.connections, secrets, runtime.bindings, runtime.receipts
) as service:
    ...
```

모델 연결 등록·수정은 `await runtime.connections.register(connection)`와 `await runtime.connections.update(connection, expected_revision)`를 사용한다. 현재 포트의 조회 계약과 별개인 어댑터 쓰기 API이며, 향후 설정 서비스에서 공급자 검증·목록·삭제 정책과 함께 감싼다. 연결 등록 성공만으로 모델의 실행 가능성을 판정하지 않는다.

기본 CLI는 계속 기존 메모리 경로를 사용한다. 방 본문이 메모리인 조합에서 내부 DB만 재열었다고 대화 복구 성공으로 표시하면 안 된다. 접수표가 확정됐는데 방 기록이 없으면 기존 계약대로 오류를 반환한다. 내부 바인딩·접수표의 방별 삭제는 논리적 행 삭제이며, 전체 방 파일 정리·백업 삭제·디스크 잔여 바이트의 안전한 삭제는 보장하지 않는다.

## 변경 기록

| 변경 | 이유와 영향 |
| --- | --- |
| 연결 정의·모델 선택·실행 자원 분리 | 공용 연결을 여러 방이 참조하면서 방별 모델·컨텍스트를 독립 적용하기 위함 |
| 독립된 방 ID와 revision 도입 | 외부 주소로 방을 식별하던 기존 구조를 대체하고 편집·삭제 중 늦은 결과 차단 |
| 비동기 저장소·모델 실행 포트 도입 | 물리 저장 선택과 무관하게 가짜 연결로 계약 검증, 이후 실제 저장소로 교체 |
| 입력 접수와 결과 기록 분리 | 송신 성공한 턴만 메모리에 추가하던 이전 계약에서 처리 상태와 중복 키를 분리 |
| 기존 CLI와 새 조립 경로의 단계적 전환 | 기존 회귀 검증을 유지하면서 새 방 구조를 먼저 검증 |
| 저장 전 모델 검증 포트 추가 | 잘못된 옵션을 저장 성공으로 처리하지 않음. 공통 타입·유한성과 공급자 범위를 분리하고 LM Studio의 기존 설정 검증기를 재사용. 실행 어댑터와 테스트 대역은 부작용 없는 `validate()`를 구현해야 함 |
| 방 모델 설정과 내부 실행 바인딩 분리 | `RoomModelConfig`·`RoomRuntimeBinding`·`RoomBindings` 도입. 방 생성/편집과 연결 지정을 분리하고 미연결 조회·편집 및 generation 검증을 추가 |
| 외부 입력 식별자와 방 저장 입력 분리 | `InputReceipts`·`InputReceipt`·`StoredRoomInput` 도입. 내부 전역 중복 키로 대상 방을 고정하고, 접수 확정 실패·본문 누락 시 모델 실행을 차단. 호출자는 접수 저장소를 추가 주입해야 함 |
| 내부 운영 데이터의 SQLite 어댑터 추가 | 모델 연결·바인딩·접수표의 재열기 보존과 DB 내 CAS 구현. 새 파일 생성과 기존 파일 열기 분리, 오류 시 실패, 스레드 작업 완료 뒤 취소 전파. 방 DB·registry·삭제 복구 없이 전체 재시작 보존으로 해석하지 않음 |
| 웹 MVP 이후로 메신저 전환 이동 | 저장·웹 대화를 먼저 검증하고 메신저 수신/전송의 추가 상태를 그 위에 연결하기 위함 |

후속 수정은 이 표에 이유와 호환성 영향을 추가하고, 구현 사실과 검증 결과는 프로젝트 작업 원본에 갱신한다. DB 경계와 메신저 송신 정책이 바뀌면 [ERD](데이터설계.md)와 이 계약을 함께 조정한다.
