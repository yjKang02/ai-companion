# MADR-003: 내부 연결 DB와 외부 방별 SQLite 분리

- 상태: 승인됨 — 사용자가 방마다 별도 SQLite·폴더를 사용하고 방 컨텍스트도 해당 DB를 원본으로 관리하는 구성을 선택했다.
- 결정일: 2026-09-19
- 관련 작업: [I01 작업 원본](../프로젝트.md#작업-목록)

## 배경

연결 설정은 개인 설치에 남기고 페르소나·대화방은 사용자 지정 외부 위치에 보관하려는 요구가 있다. [저장 구조 검토안](../외부라이브러리-저장구조-검토안.md)은 방별 DB와 라이브러리 공용 DB, 방 컨텍스트의 파일 원본과 DB 원본을 비교했다. 사용자는 방 단위 이동·공유에 유리한 방별 SQLite와 DB 원본 방식을 선택했다.

## 결정

1. 모델·메신저 연결과 장치별 실행 바인딩은 앱 전용 내부 DB에 보관한다. 내부는 설치 디렉터리가 아니라 개인 설치의 지속 데이터 영역을 뜻한다.
2. 개인·캐릭터 페르소나 원본은 사용자 지정 외부 라이브러리의 텍스트 파일로 보관한다.
3. 외부 라이브러리에서 방마다 독립된 폴더와 SQLite DB를 사용한다. 방 이름·컨텍스트 사본·모델 옵션·대화 기록은 해당 방 DB의 원본이다.
4. 같은 컨텍스트를 DB와 Markdown 양쪽의 수정 가능한 원본으로 중복 관리하지 않는다. 방 컨텍스트의 파일 표현은 이후 내보내기·가져오기 기능으로 취급한다.
5. 방을 다른 설치로 옮겨도 기록과 컨텍스트를 읽을 수 있어야 한다. 모델·메신저 실행 연결은 새 환경에서 다시 지정한다. 키·토큰·외부 채팅 주소는 방의 실행 설정에 넣지 않는다.

API 키·봇 토큰의 원문을 내부 DB에 평문으로 넣기로 결정한 것은 아니다. DB에는 비밀 참조만 두고 보호된 저장 방식은 별도로 결정한다. 방의 대화 본문에 사용자가 입력한 개인정보까지 자동 제거한다는 보장도 아니다.

## 결과와 비용

방 내부의 저장 일관성과 내부 운영 DB 사이의 복구를 구분해야 한다. DB 간 참조·삭제는 하나의 FK나 일괄 CASCADE에 맡기지 않으며, 방별 마이그레이션과 미완료 작업 복구가 필요하다. 라이브러리를 찾을 수 없다고 빈 방 DB를 자동 생성하지 않는다.

이 결정은 폴더를 이동·공유하기 좋은 저장 단위를 정한 것이다. 실행 중인 DB 파일을 임의 복사해도 안전하다는 의미나 공유·백업 기능의 구현 완료를 뜻하지 않는다.

- 비밀 저장소의 OS별 구현, 데이터 경로의 기본값과 이전 UI.
- 백업·내보내기·복제·복원의 패키지 형식과 동기화.
- 웹 프레임워크·실시간 통신, Telegram·스케줄러 구현.
