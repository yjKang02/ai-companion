# MADR-002: 로컬 서버와 로컬 웹 UI로 구현

- 상태: 승인됨 — 사용자가 초기 구현 방식을 로컬 서버 + 로컬 웹 UI로 결정했다.
- 결정일: 2026-09-17
- 관련 작업: [D01 작업 원본](../프로젝트.md#작업-목록)

## 1. 배경과 문제

[UI 설계](../UI설계.md)는 대화 프로필 목록, 실시간 직접 채팅, 우측 방 설정과 스케줄러 제어를 요구한다. 개인 서버의 웹 화면과 서버를 포함한 설치형 앱을 비교했으며, 사용자는 우선 로컬 서버와 로컬 웹 UI로 구현하기로 선택했다.

## 2. 결정

사용자 PC에서 백엔드 서버를 실행하고 같은 PC의 브라우저로 로컬 웹 UI에 접속한다. 기존 Python 백엔드가 대화 처리·영구 저장·모델 호출·메신저 연결과 향후 스케줄러 실행을 담당하고, 웹 UI는 조회·입력·설정 편집·실시간 상태 표시를 담당한다.

브라우저 창과 백엔드 실행 수명을 분리한다. 브라우저를 닫아도 서버가 실행 중이면 메신저 처리와 활성화된 스케줄러는 계속 동작한다. 서버 종료 또는 PC 종료·절전 중에는 실행을 보장하지 않는다. 대화와 설정은 종료 시점이 아닌 각 저장 처리 시 영구 보존한다.

초기 접속 범위는 같은 PC의 로컬 UI다. 서버는 루프백 주소로 제공하는 것을 기본으로 하며 LAN·인터넷 공개 접속은 이번 결정 범위에 포함하지 않는다. 외부 모델 API와 메신저 연결은 별개이므로 로컬 UI라는 이유로 모든 처리가 오프라인이라는 의미는 아니다.

## 3. 검토한 대안

- 서버를 포함한 설치형 앱: 트레이·메뉴 막대와 실행 통합이 가능하지만 OS별 패키징과 프로세스 관리가 필요해 후속 확장 후보로 남긴다.
- 별도 상시 서버 + 웹 UI: 사용자 PC가 꺼져 있어도 운영할 수 있으나 별도 서버 운영과 원격 접근 설계가 필요해 현재 선택하지 않는다.

## 4. 선택 이유와 결과

사용자의 현재 선택에 따라 웹 화면과 기존 대화 백엔드의 연동부터 구체화한다. 화면과 실행 로직을 분리하면 향후 설치형 앱으로 묶거나 별도 서버에 배치하는 선택을 검토할 수 있다. 두 형태의 동시 지원을 약속하는 결정은 아니다.

초기 버전에서는 사용자가 로컬 서버를 실행해야 한다. 서버 종료 중 놓친 일정과 중단된 작업의 복구 정책은 별도 설계가 필요하다. 로컬 접속에서도 API 접근과 브라우저 변경 요청 보호 방식은 구현 전에 정한다.

## 5. 남은 선택

- 백엔드 웹 프레임워크, 프런트엔드 프레임워크와 UI 컴포넌트 라이브러리.
- 실시간 갱신 방식, API 계약과 로컬 접속 인증.
- 실행·종료 방법, 포트와 데이터 경로, 지원 OS별 검증 범위.
- 스케줄러의 재시작·절전 복귀 처리와 놓친 일정 정책.
- 향후 트레이 실행부, 로그인 시 자동 실행, 설치형 배포의 도입 여부.

이 문서는 구현 방식의 결정이며 로컬 서버·웹 UI·스케줄러가 구현되었다는 기록은 아니다.
